# tfc-admin

Declares the whole Terraform Cloud / HCP Terraform layer as code (audit C3): every
deployable root's workspace plus the native TFC controls around it. It declares NO
cloud provider, so it needs no cloud credentials, only a TFC token (`TFE_TOKEN`).
Create its own `tfc-admin` workspace by hand once, then it manages all the others
and adopts itself via an import block (`manage_tfc_admin_workspace`, default true). Only
a managed tfc-admin workspace gets `speculative_enabled = false`. An unmanaged one keeps
TFC's default, so any PR's plan could read its org-admin `TFE_TOKEN`; a `check` warns
when it is unmanaged and VCS-connected.

## Configuration: `config/landing-zone.yaml`

tfc-admin reads the committed single-source config (`landing_zone_config_path`, default
`../../config/landing-zone.yaml`; `""` disables it). Precedence: explicit variable > config file >
built-in default.

| Input | Config key |
|-------|------------|
| `tfc_organization` | `org.tfc.organization` |
| `enable_gcp` / `enable_aws` / `enable_saas` | `gcp.enabled` / `aws.enabled` / `saas.enabled` |
| `gcp-workload-<env>` workspaces | keys of `gcp.environments` |
| `aws-workload-<env>` workspaces + their `workload_account_key` | `aws.workload_environments[<env>].account_key` |
| `saas_workspaces` | `saas.workspaces` |
| Project names | `org.tfc.project_name_prefix` (`<prefix><cloud>`), or `org.tfc.gcp_project` / `aws_project` / `saas_project` / `platform_project` / `guardrails_project` (+ `gcp_workloads_project` / `aws_workloads_project` when split) |
| `split_workload_projects` | `org.tfc.split_workload_projects` |
| Production workloads (no speculative plans) | `gcp.environments[<env>].is_production` / `aws.workload_environments[<env>].is_production` (required on every environment) |
| `vcs_repo` | `org.tfc.vcs_repo` (IDs only, no secrets) |
| `gcp_project_prefix` (derived workload SA emails) | `org.prefix` (the key gcp-bootstrap reads as `project_prefix`) |

An explicit `environments` variable replaces both derived environment lists, as before. Per-workspace
values from `config/tfc-workspaces.yaml` and `workspace_variables` still override the derived ones.
`org.tfc.aws_project` is also read by `aws-organization` (`tfc_project`), so the member-account OIDC
trust and the workspace project cannot drift apart.

**Provider and tier.** The `tfe` provider is pinned `>= 0.83.0, < 1.0.0`. Health assessments
(`enable_health_assessments`, default on) and policy sets (`enable_policy_sets`) need a **paid HCP
Terraform tier**; on the free tier, set `enable_health_assessments = false` and leave policy sets off.

## What it manages

| Control | How |
|---------|-----|
| Workspace catalog | One local, `local.catalog` in `main.tf`, is the only hand-maintained workspace inventory: each entry gives a root's `dir`, `cloud`, `desc`, `tags`, run-trigger `upstreams`, remote-state `reads`, and optionally `aws_member_aliases`, `aws_management_account`, `security_only` and `per_environment` (expanded to `<key>-<env>` per configured environment; saas: per `saas.workspaces`). The workspaces, run triggers, consumer graph, alias env vars and management-default list are all derived from it (output `workspace_catalog`). Adding a root: [adding-a-cloud](../../docs/architecture/adding-a-cloud.md#7-register-the-workspace-in-the-tfc-admin-catalog). |
| Cloud selection | `enable_gcp`, `enable_aws`, `enable_saas` + `saas_workspaces` (or `<cloud>.enabled` / `saas.workspaces` in `config/landing-zone.yaml`), all default **false**; at least one must be true (validation). Each estate gets only the workspaces of the clouds it enables. |
| Execution mode | `execution_mode` (remote/agent) for every workspace, overridden per workspace by `workspace_execution_modes`. Default `{ gcp-bootstrap = "local" }`: the GCP phase-0 apply runs on the operator's machine with ADC while TFC stores state. Set `{}` after the second bootstrap pass. `local` is accepted only for `gcp-bootstrap` / `aws-organization`. |
| Projects + team access | One `tfe_project` per cloud in use (`<prefix>gcp/aws/saas/platform`; `split_workload_projects` adds `<prefix>gcp-workloads` / `<prefix>aws-workloads`). Least privilege: on a project holding control-plane workspaces, `platform_team_id` gets only **custom** access (`runs = platform_team_control_plane_runs`, default `plan`; variables and state read-only; no locking, workspace create/delete/move, run tasks or policy overrides), and `control_plane_approvers_team_id` (a small, separate team) gets custom `runs = apply` with variables read-only, so the person who changes control-plane code or inputs cannot also confirm the apply. **Secret-bearing projects:** a plan, including a CLI speculative plan of the member's own unreviewed configuration (`speculative_enabled = false` does not stop those), runs code with the workspace's environment variables. A workspace is secret-bearing when tfc-admin writes it a sensitive variable or a variable whose key looks like a secret (`*_TOKEN`, `*_SECRET`, `*_SECRET_KEY`, `*_SERVICE_ROLE_KEY`, `*_PASSWORD`, `*_PASSWD`, `*_PASSPHRASE`, `*_PRIVATE_KEY`, `*_API_KEY`, `*_ACCESS_KEY`, `*_CREDENTIALS`), when it sets `enable_saas_secret_bridge` to anything but an explicit false (`false`, `0` or empty; its `TFE_TOKEN` may be set by hand), when it is the self-managed tfc-admin workspace (`TFE_TOKEN`) or a `saas-*` workspace (account-wide Supabase/Vercel tokens), and every workspace except gcp-guardrails is secret-bearing when `common_workspace_variables` carries such a value. On every project that holds one, the platform team gets `runs = read` whatever `platform_team_control_plane_runs` says, the approvers team confirms runs (except on the tfc-admin project, and on the saas project when `saas_approvers_team_id` is set: that dedicated team then confirms `saas-*` applies, and a `check` warns while it is unset, because a confirmer can also queue a plan that reads the Supabase/Vercel tokens), and the workspace gets no workspace-level platform write. Marking a secret `sensitive = true` is the contract; the name pattern is defence in depth for a secret that was not marked. With one project per cloud, a secret-bearing workload therefore also puts the control plane at `runs = read`; a `check` warns and recommends `split_workload_projects = true`. Another `check` warns when a platform team is set without `control_plane_approvers_team_id` while a secret-bearing project other than tfc-admin's exists: only organization owners can then run it. **Production workloads** (`gcp-workload-<env>` / `aws-workload-<env>` whose environment sets `is_production: true`) get the control-plane treatment: their project grants the platform team the same custom access (no variable edits, so no `TF_VAR_*` that beats `config/landing-zone.yaml`, and no apply) and the approvers team `runs = apply`, so one person cannot change a production input and confirm the apply. They are tagged `tier:production`. A project holding only non-production workloads gives the platform team fixed **write**; a non-production workload sharing a project with the control plane or with a production workload gets write through a workspace-level `tfe_team_access` (in both `split_workload_projects` modes). **State export:** `state_backup_team_id` (a dedicated, hand-created team) gets custom `state_versions = read` (runs read, variables none) on every project except guardrails and saas (`enable_saas_state_backup = true` adds saas), for [`state-backup.yml`](../../docs/runbooks/state-backup.md). `viewer_team_ids` get fixed **read** on every project except guardrails and saas. Fixed read includes the full state file, and `saas-*` state holds the Supabase database password and service-role key, so on the saas project viewers and the platform team get custom access instead: runs and variables read, `state_versions = none` (read-outputs can still return a sensitive output through the API; bridging workloads read saas outputs with their own reader team token). With AWS, enable the split only after the workload accounts' OIDC trust names the workloads project (`aws-organization` `tfc_workspace_bindings[*].project`). **Guardrails:** `gcp-guardrails` (org IAM deny policies) always gets its own `<prefix>guardrails` project (`org.tfc.guardrails_project` overrides the name) where only `security_team_id` has access (custom: `runs = apply`, variables/state read-only); no platform, approvers or viewer grant, and a `check` warns while `security_team_id` is null. The one other grant is the optional `guardrails_release_reader_team_id` (a dedicated, hand-created team whose token is the GitHub secret `TFC_TOKEN_GUARDRAILS`): custom `runs = read`, no state, no variables, no locking, so `terraform-apply.yml` can verify `gcp-guardrails/v*` release tags. **SaaS bridge readers:** `saas_outputs_reader_team_ids` maps each `saas-<name>` workspace to its own hand-created, dedicated team, which gets custom access on that one workspace with `state_versions = read-outputs`, runs read-only and no variables, and nothing anywhere else; an owner creates its expiring token by hand ([saas-bootstrap](../../docs/runbooks/saas-bootstrap.md#bridging-secrets-to-a-workload-and-rotating-them)). |
| Trigger patterns | Each VCS workspace triggers on `<working_dir>/**`, on the module trees its root composes (`local.root_trigger_dirs`, keyed by root dir: the transitive closure of its local module sources, plus `examples/presets` for `gcp-workload-<env>`; `scripts/check-consistency.sh` fails when the map is missing or lists a module), so a module-only PR queues plans only where that module is used, and on its estate's own config: the landing-zone file + `workspace_variables_file` for production (`config/landing-zone.yaml` + `config/tfc-workspaces.yaml`), `<dir>/**` for any other estate (`config/sandbox/**`), derived from `landing_zone_config_path` / `workspace_variables_file` (a relative path that leaves the repo fails the plan). Editing one estate's YAML never queues the other's runs ([sandbox estate](../../docs/guides/sandbox-estate.md)). A production config edit (`config/landing-zone.yaml` or `config/tfc-workspaces.yaml`) still queues a plan on **every** production workspace, because every root reads that one file. |
| Speculative plans | Off (`speculative_enabled = false`) for `speculative_disabled_workspaces` (the control plane + `tfc-admin`), always for `gcp-guardrails` and, with `disable_speculative_on_production` (default true), for every production workload workspace, and, with `disable_speculative_on_saas` (default true), for every `saas-<name>` workspace (static account-wide Supabase/Vercel tokens, no plan identity), and for every other secret-bearing workspace (see the access row) unless `enable_speculative_on_secret_bearing = true`. So a PR's code never runs with a privileged, production or SaaS-account credential. Control-plane workspaces also disallow UI destroy plans. |
| Auto-apply | `auto_apply` is off everywhere by default. Workload workspaces whose environment sets `is_production: false` **explicitly** get `queue_all_runs` and `auto_apply_run_trigger` (`enable_nonprod_workload_auto_apply`; the null default turns it on only while the policy sets, and so `destroy_guard`, are attached): a run queued by a confirmed upstream apply applies without a second confirmation. An omitted `is_production` fails closed. The run `queue_all_runs` starts at creation is expected to fail, because the identity does not exist yet; the setting lets later runs queue without a manual first run. Production workloads and every shared workspace keep manual confirmation. `auto_apply_on_merge = true` (the sandbox estate) sets `auto_apply` and `auto_apply_run_trigger` on every workspace except `tfc-admin` and `gcp-guardrails` (output `never_auto_apply_workspaces`), so a merge applies the changed roots and run triggers carry it down the DAG. |
| Run triggers | `enable_run_triggers` (default true): `tfc-admin` is the DAG root and triggers `gcp-bootstrap` (once it runs remotely) and `aws-organization`; each root then triggers its direct downstream roots and the workloads. A trigger fires only when its source **applies** (not on a no-op, not from a local-execution apply). |
| Remote state | `global_remote_state = false` everywhere; `remote_state_consumer_ids` encode the real read graph from `envs/**` `terraform_remote_state` blocks. Opt-in cross-cloud edges (saas secret bridge, cross-cloud references) via `extra_remote_state_consumers`. |
| Health assessments | `enable_health_assessments` (default true): native drift detection + continuous validation. |
| Dynamic credentials | Per-workspace `TFC_GCP_*` / `TFC_AWS_*` env vars, set only when their inputs are supplied (see below). The multi-account roots `aws-security` / `aws-backup` get the management role (`aws_management_plan_role_arn` / `aws_management_apply_role_arn`) as their default configuration plus a `TFC_AWS_PROVIDER_AUTH_<alias>` / `TFC_AWS_PLAN_ROLE_ARN_<alias>` / `TFC_AWS_APPLY_ROLE_ARN_<alias>` set per member-account alias (`security_tooling`, `log_archive`, `forensics`; `backup`), derived from aws-organization `tfc_*_role_arns` or `aws_alias_role_arns`. They get nothing until every alias has roles. `aws-organization` gets the management role. |
| Variables | Org-wide values in the `<prefix>common` variable set (attached to every workspace except `gcp-guardrails`, so platform-controlled values cannot reach the security team's workspace). Per-workspace values come from a committed `config/tfc-workspaces.yaml` (`workspace_variables_file`, read only if present; no secrets; see `config/tfc-workspaces.example.yaml`) and `workspace_variables` (wins). `gcp-workload-<env>` / `aws-workload-<env>` get `environment` derived from the name; `aws-workload-<env>` also gets `workload_account_key` from `aws.workload_environments[<env>].account_key` (or `environments[<env>].aws_account_key`). |
| Policy | Two OPA policy sets, both from the VCS repo and attached to every managed workspace (`enable_policy_sets`; null = on when `vcs_repo` is set and `org.tfc.plan` / `tfc_plan` is `standard` or `premium`, else off and a `check` warns that destructive changes are unguarded). `<prefix>opa-guardrails` (`policies/opa/`): 14 mandatory + 3 advisory, **not overridable** (`policy_set_overridable`, default false). `<prefix>destructive-change-guard` (`policies/opa-destructive/`): the mandatory `destroy_guard` on stateful deletes and replaces and `tfc_admin_guard` on policy-set detachment, auto-apply on control-plane or production workspaces and widened team access, **overridable**. Both sets also judge the `tfc-admin` workspace, even when it is not self-managed. Overrides belong to the hand-created security team (`security_team_id`), which an owner grants Manage Policy Overrides in the HCP UI; tfc-admin creates no teams and sets no organization access. `opa_version` is pinned so that an OPA release cannot change results unreviewed. |

## Variables belong in code

Control-plane inputs (for example gcp-organization `gcp_overrides` and aws-security
`aws_overrides`, which hold `enable_admin_containment` and `break_glass_trusted_principals`) must come from `config/landing-zone.yaml`,
`config/tfc-workspaces.yaml` or `workspace_variables`, all reviewed in a PR. TFC cannot forbid
an organization owner from setting a variable in the UI, so this is enforced by permissions, not
by Terraform: no team this root grants has `variables = write` on a control-plane project, and
tfc-admin reverts any drift on the variables it manages at its next apply. Review the workspace
variables in health assessments and audit-trail events for UI edits by owners.

## Two-pass bootstrap (dynamic credentials)

The plan/apply identities are created by roots whose workspaces this root creates:

1. Apply tfc-admin: workspaces exist, no credential env vars yet.
2. Apply `gcp-bootstrap` (phase-0) and/or `aws-organization`.
3. Feed their outputs back, either by copying them into
   `gcp_workload_provider_name`, `gcp_plan_service_accounts`, `gcp_apply_service_accounts`,
   `aws_plan_role_arns`, `aws_apply_role_arns` (maps keyed by workspace name), or by
   setting `gcp_bootstrap_outputs_from_tfc` / `aws_organization_outputs_from_tfc = true`
   (read via `tfe_outputs`; AWS maps each single-account workspace => account key from
   aws-organization `tfc_workspace_bindings`, `environments[<env>].aws_account_key` or
   `aws_workspace_account_keys`). tfc-admin is then added as a remote-state consumer of those producers.
4. Re-apply tfc-admin, with `workspace_execution_modes = {}` so `gcp-bootstrap` moves to
   remote execution (a `check` warns while `gcp_bootstrap_outputs_from_tfc` is on and
   `gcp-bootstrap` is still local: tfc-admin's run trigger cannot reach a local workspace).

After this pass, a new GCP environment needs no second tfc-admin pass: with
`gcp_bootstrap_outputs_from_tfc`, tfc-admin derives each `gcp-workload-<env>`'s SA emails as
`<prefix>-wl-<env>-{plan,apply}@<admin_project_id>.iam.gserviceaccount.com` (`<prefix>` from
`gcp_project_prefix` / `org.prefix`, `admin_project_id` from the static gcp-bootstrap output). A
`check` warns when a derived email differs from one gcp-bootstrap already outputs, and the plan
fails when `<prefix>-wl-<env>-apply` exceeds the 30-character GCP account-ID limit. Greenfield still
needs the phase-0 pass above: nothing is derived until gcp-bootstrap has outputs.

See [docs/runbooks/bootstrap.md](../../docs/runbooks/bootstrap.md) and
[docs/guides/CI_SECRETS.md](../../docs/guides/CI_SECRETS.md).
